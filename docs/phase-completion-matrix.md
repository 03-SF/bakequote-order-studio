## Scope reconciliation

- **English only:** the explicit later owner instruction supersedes original English/Urdu and RTL requirements. Normal direction-aware APIs, accessibility and larger text remain useful.
- **Offline functionality is excluded** by the current owner instruction. Existing local unsent-draft/session persistence and image-cleanup bookkeeping are recovery mechanisms, not a commitment to browse, edit, queue or submit offline. Preserve safe network-error handling, session restoration, unsent input and idempotent explicit retries; authoritative operations require an online response. Historic offline requirements/benchmarks are superseded.
- **Lifecycle:** the owner explicitly selected the original Confirmed → Baking → Ready → Delivered sequence. Mandatory Decorating first appeared in `f057a16`; migration `20261029000800_original_production_lifecycle.sql` prevents new transitions into it. Existing Decorating orders and history remain intact; they continue to consume capacity and may advance to Ready. No data is rewritten. The original reference and `ea5966f` use the same approved sequence.
- **Billing and backup:** the original requirements describe *applicable* plans/export/restore and prohibit invented commercial terms; the later supplied Phase 9 scope explicitly names billing recovery, encrypted backup/restore and account deletion. These are desired outcomes, not evidence of implemented providers or approval of a particular entitlement, price, retention period, encryption format, archive contents, recovery promise, RPO or RTO. Apple/Google sandbox testing was requested in the later release scope, but product IDs, provider account access and plan rules are still missing. Source backup, database recovery and user export are separate concerns.
- **Dual-role and membership:** same-identity customer/baker enrollment is unresolved. Preview role switches never grant real access.
- Android installation/native-device acceptance, iOS build/device testing, native callbacks/storage/permissions and push acceptance remain deferred by the owner. Flutter Web is a laptop test host, not a change in Android/iOS product direction.

## Credential incident

The previously exposed value was a Supabase **secret API key** (the `sb_secret_` type), an elevated server credential that bypasses RLS. It was supplied in chat; its value is not reproduced here. Its rotation/revocation is **unconfirmed**, and the prior local credential scan cannot prove rotation. Flutter uses the publishable client key; no privileged key belongs in Flutter, Git or chat.

If not already done, in the confirmed **development** project: open **Settings → API Keys**, create a replacement secret key if a server component actually requires one, update each authorized server-side secret store, verify those components use the replacement, then delete the exposed secret key after confirming dependencies. Do not delete keys blindly if their consumers are unknown. If no component uses it, identify the exposed key privately in the Dashboard and retire it. Verify the old key is absent/revoked using the Dashboard or an appropriately authorized operator, without sending either key to chat; report only “rotated/revoked” or “not yet/unsure.” This procedure follows [Supabase's compromised-key guidance](https://supabase.com/docs/guides/getting-started/api-keys#rotate-a-leaked-or-compromised-key). A new secret key does not itself retire an old key; deletion is a distinct action. Do not assume a database-password, management-token or JWT-signing-key rotation occurred.

Local dependency inspection: `config/local.json` and `config/web.local.json` contain the public URL/client key and callback configuration, with no detected secret/service-role key. `config/email-check.local.json` stores ordinary customer credentials, not the Supabase secret key. Flutter and the HTTP acceptance scripts read the publishable key and ordinary user sessions. The Supabase CLI uses its own authenticated management/login and database-link mechanism, distinct from this exposed project secret. No Edge Function directory or local script consumer of the exposed key was found. This inspection cannot identify remote services, Dashboard webhooks or external secret stores: check those privately before revocation. If an external server consumer exists, update its server-side secret store; the Flutter JSON files should continue to hold only the publishable key.

## Phase 5–6 live acceptance setup

1. Use the confirmed hosted **development** project and keep email confirmation enabled. Prepare three distinct accounts with accessible inboxes: one Customer and two Bakers. Verify them through normal email confirmation and complete initial onboarding. The provider's default sender may only deliver to permitted organization-member addresses; use authorized SMTP for other test inboxes if needed. Administrative confirmation is not evidence of delivered verification email.
2. With Baker A, use a dedicated disposable activated test bakery with an active product, configured timezone/fulfilment and **daily capacity 1**. Choose a future service date with no bookings and availability `available`. Existing business data is not reset or automatically modified.
3. Once the accounts and dedicated bakery are ready, the assistant can run the Phase 5 test twice to create **two separate Pending test requests** for the same bakery and future date, each with a private reference image. Pending requests do not reserve capacity. The test refuses to overwrite an existing unsent draft and retains these disposable records. Alternatively, create both manually and provide their IDs locally with `-Mode List` and `-Mode Fixtures` below. Do not use real customer information.
4. Open PowerShell in `mobile` and run the setup helper. Choose **YES** when asked to reuse the existing local customer fixture; its confirmed email and Customer onboarding were verified through a normal login. Enter the two baker emails and passwords locally when prompted. The helper stores `PSCredential` entries in ignored `config/acceptance-accounts.local.xml`; on Windows the password fields are protected using the current Windows user's DPAPI, while email addresses are not encrypted. It is usable only by the same Windows account on the same machine. This is local test configuration, not a backup. Do not paste passwords, tokens or the file contents into chat. The older `config/email-check.local.json` customer fixture is ignored but contains a plaintext password; keep it private and remove it only when you have another safe way to access the test account.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/acceptance_accounts.ps1 -Mode Setup
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/acceptance_accounts.ps1 -Mode Preflight
# Tell the assistant setup is complete; it can create the dedicated fixtures.
# Only if you created the two requests manually instead:
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/acceptance_accounts.ps1 -Mode List
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/acceptance_accounts.ps1 -Mode Fixtures
```

The ignored credential XML contains entries named `CUSTOMER`, `BAKER_A` and `BAKER_B`, each a Windows `PSCredential` with an email username and protected password. You do not need to edit the XML. The existing ignored `config/local.json` has `APP_MODE`, `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` and `AUTH_CALLBACK_BASE`; it never needs the secret API key. When automatic fixture creation is used, the ignored `config/phase6-fixtures.local.json` contains `order_one`, `order_two`, `business_id`, `service_date` and `project_url`; manual fixture entry stores just the two order IDs. These IDs are local test identifiers, not passwords.

Once local setup and the dedicated bakery are ready, the assistant can run `-Mode CrossAccount`, `-Mode Phase5` twice and `-Mode Phase6` under the same Windows account without receiving the passwords. The Phase 5 runner records two Pending test requests, refuses to overwrite an existing unsent draft and does not reset the bakery. The Phase 6 runner verifies the configured URL matches the CLI-linked hosted project, identities/ownership, one-slot availability and fixture state; the operator must still confirm that the linked project is development. It checks owner/customer visibility, unrelated baker denial and unchanged bytes/rows, quote revision and invalidation, stale agreement, synchronized normal-user HTTP confirmation requests, exact retry/different-input rejection, fresh-session persistence, and Confirmed → Baking → Ready → Delivered. It intentionally leaves one test order Delivered and one Pending. The client barrier starts requests together; it does not prove database overlap, so collect server-side timing/lock evidence for a true concurrency claim. A successful HTTP runner is not Chrome visual acceptance. No service-role credential is used to prove user permissions.
